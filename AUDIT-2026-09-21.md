# Security Audit: Lootbox (pina-rs/lootbox)

- **Date:** 2026-09-21
- **Scope:** Full-repository deep audit per the solana-audit skill methodology (3 loss layers: code, operations, economics)
- **Commit / branch:** `fix/revert-prepared-release`, HEAD `dc6effd`
- **Program:** `Bp6AJD3QQ64kZVfc1YnhP7GN5UBYEHsDXpGUc1xzg4op` (Pina 0.19 / Pinocchio, `no_std`, non-Anchor)
- **Status:** Pre-release, no mainnet deployment (per AGENTS.md policy) — deployed-artifact verification not applicable
- **Prior internal audit:** `EXPLOIT-HUNT-2026-09-19.md` (this audit independently re-verified its findings and found one new High it missed)

## Executive summary

**Findings: 1 High, 2 Medium, 5 Low, 3 Informational.**

The on-chain program is unusually well-hardened for a pre-release codebase: every instruction re-derives its PDAs against canonical bumps, post-CPI state is re-verified against Switchboard, escrow accounts reject delegates/close-authorities/freeze, arithmetic is checked throughout, `[profile.release] overflow-checks = true` is set, and rejection sampling is correctly unbiased. The pina framework trust base (`send_owned`, `close_account_zeroed`, bump validation, compact-account hidden-tail rejection) was verified sound.

**The single biggest risk is a missing admission check on Metaplex Core prize assets (H1).** The program escrows Core assets by transferring ownership to the bundle PDA but never inspects the asset's plugin registry. Core's `PermanentTransferDelegate` plugin — settable only at asset creation, defaulting to the update authority, and _persisting across transfers_ — lets the original creator steal the asset back out of the winner's wallet after delivery. I verified this against the exact pinned upstream commit (`83131e0`) the program's own CPI comment cites. This is the Cashio class: the program validates _who owns the account_ but not _what other authorities still control it_.

Medium findings are the forfeit-path value loss (re-confirmed from the prior audit) and mutable Token-Metadata prizes (re-confirmed). The ops layer is appropriately honest for pre-release: CI is SHA-pinned, `cargo deny` advisories pass, upgrade-authority policy is a documented release gate. No Critical was found: there is no anonymous path to escrowed funds, double claims, or randomness bias.

## Findings

### H1 — Core prize assets admit `PermanentTransferDelegate` theft after delivery, High

- **Location:** `programs/lootbox_program/src/templates/collections.rs:486-507` (`validate_core_accounts`), used by `FundCoreAssetPrize` / `ClaimCoreAssetPrize` / `ReclaimCoreAssetPrize`; the admission comment at `collections.rs:496-499`.
- **Mechanism:** The program validates a Core prize asset by checking only: `core_program == MPL_CORE_ID`, `asset.owner == MPL_CORE_ID`, `collection.address == MPL_CORE_ID`, and `plugin_accounts.is_empty()`. The `plugin_accounts` slice is the _instruction's_ remaining accounts — it says nothing about the plugins already stored **inside the asset account's plugin registry**. The asset account data (an `AssetV1` plus optional `PluginHeaderV1`/`PluginRegistryV1`) is never read.
- **Upstream evidence (verified against the program's own pinned commit `83131e07872b9e98dcdb6dde8ec53931813c0d20`):**
  - `AssetV1::validate_transfer` approves only the current owner — but `PluginType::check_transfer` maps `PermanentTransferDelegate` to `CheckResult::CanApprove`, and the plugin's `validate_transfer` returns `ForceApproved` when the signer matches the plugin authority, bypassing the owner check entirely (`plugins/permanent_transfer_delegate.rs:45-59`, `plugins/lifecycle.rs:95-104`).
  - The plugin "can only be added at creation time" (`validate_add_plugin` → `Rejected`), and its default authority is **the update authority at mint** — i.e., the creator. It cannot be removed by the owner; `PluginType::PermanentTransferDelegate → Authority::UpdateAuthority` (`plugins/mod.rs:165`).
  - Owner-managed plugin authorities are reset on transfer, but permanent plugin authorities are not.
- **Exploit scenario:**
  1. Attacker creates a Core asset with `PermanentTransferDelegate` authority = attacker (one tx, at creation — costs nothing extra).
  2. `FundCoreAssetPrize`: the asset transfers to the bundle PDA. All checks pass — owner is MPL Core, no plugin _accounts_ are passed, `collection` slot holds the Core program ID.
  3. A holder wins and claims: `ClaimCoreAssetPrize` transfers the asset to the beneficiary. The lootbox signs as the bundle PDA; the claim succeeds and the winner now _owns_ an asset the attacker can still move.
  4. Attacker calls Metaplex Core `TransferV1` directly (no lootbox involvement) with `authority = attacker`, `new_owner = attacker`. The permanent delegate's `ForceApproved` short-circuits validation and the asset leaves the winner's ownership.
- **Severity justification:** Loss of a unique prize NFT under realistic conditions, requiring only a malicious creator — the same actor the protocol explicitly models (the security notes table lists creator threats). Value loss is unconditional once a delegated asset is admitted: escrow and delivery work perfectly, then the prize is stolen post-delivery. The program's own admission policy ("only plain, uncollected Core assets… avoiding mutable transfer delegates") is not actually enforced. This is the Cashio circular-trust pattern: proving the account's owner while ignoring a coexisting authority that also controls the asset.
- **Note on the pinned ABI:** at commit `83131e0`, Core's transfer account set is `asset, collection, payer, authority, new_owner, system_program, log_wrapper` + adapters, and the program's `invoke_core_transfer` builds exactly this (discriminator `[14, 0]`, `collections.rs:442-484`). The current upstream adds optional `system_program`/`log_wrapper` checks but keeps the same permission model (verified on `main`). So the theft works against both the pinned and current Core program.
- **Fix:** read the asset account data in `validate_core_accounts` and reject any asset whose data length exceeds `AssetV1`'s base size (i.e., has a `PluginHeaderV1`/registry), matching the "no plugins" admission policy structurally rather than by instruction accounts. Re-verify at claim time too (claims already re-derive fresh accounts, so a post-funding `add_plugin` by the creator is _not_ possible for `PermanentTransferDelegate` — it is creation-time-only; the registry check closes the creation-time trap). A devnet regression test against real Core with a delegated asset should assert funding fails closed.

### M1 — Forfeit burns the opener's box with zero compensation; bounty is front-runnable, Medium

- **Location:** `templates/opening.rs:135-160` (`record_forfeit`), `:487-534` (`ForfeitTemplateOpen`), `:162-214` (`pay_settlement_bounty`); timeout constant `lib.rs:49` (`RANDOMNESS_TIMEOUT_SLOTS = 300`).
- **Mechanism:** The box is burned at `RequestTemplateOpen` (opening.rs:377-378). If no reveal lands within 300 slots, any signer may forfeit the FIFO head: status → 4, `pending_openings -= 1`, `next_allocation` advances — and `settlement_bounty_lamports` is paid to the arbitrary `caller` (opening.rs:519-525). Status 4 can never claim (`claims.rs:379` requires status 2) and only closes for rent (`close.rs:54`). The v1 analogue (`RefundOpen`, lib.rs:1256-1290) pays the recipient the outcome floor and is recipient-gated — the template path is strictly worse for openers.
- **Exploit:** during oracle latency, wait out 300 slots, submit `ForfeitTemplateOpen{caller=attacker}`, collect the bounty and kill the opening even if a valid gateway proof lands one slot later (fulfill requires status 0; forfeit wins the race). Beneficiary permanently loses the burned box with zero compensation.
- **Severity:** real holder value loss, bounded by oracle liveness and the prepaid bounty, monetizable grief by any watcher. Design-documented (security-templates.md "Oracle and FIFO liveness") but the zero-compensation gap remains a funds-loss surface.
- **Fix:** pay the beneficiary a forfeit floor from the service vault (mirror v1), gate the bounty to a maintainers allowlist, or allow a late valid reveal for the same seed to re-open a status-4 opening.

### M2 — Bundle-path metadata NFT prizes accept mutable metadata, Medium

- **Location:** `templates/collections.rs:359-429` (`validate_metadata_accounts`); same family: `templates.rs:1486-1500` (`FundMintPrize` badge mints).
- **Mechanism:** checks supply==1, decimals==0, mint/freeze authority ∈ {None, Master Edition PDA}, metadata PDA + owner — but never reads the metadata account's `update_authority` or `is_mutable`. A creator funds a standard NFT with `is_mutable = true` and then rewrites name/URI/collection via Token Metadata `Update` after funding or after a winner holds it: a display-layer rug with correct token identity. The codebase's own stricter policy elsewhere (prize_pool.rs:438-440 rejects mutable Bubblegum metadata; box mints require a zeroed metadata update authority, templates.rs:1034-1038) shows the intended standard.
- **Severity:** prize-content integrity, not solvency — no token theft.
- **Fix:** require `is_mutable == false` (and/or pin a semantic metadata hash like the pool path) in `validate_metadata_accounts` and `FundMintPrize`.

### L1 — v1 refund floor configurable to 0, Low

`AddOutcome` accepts `reward_lamports = 0` (lib.rs:792-794); the "timeout floor" then refunds nothing (lib.rs:674-692). Creator-discretionary; fix with a `> 0` check or document it as a zero-guarantee outcome.

### L2 — `ClosePrizePool` liveness, Low

`active_pool_is_terminal` requires `claimed == assigned` (prize_pool.rs:663-686): one absent winner blocks pool rent recovery forever. No fund loss; items stay claimable. Consider a retired-forced-finalization path.

### L3 — Commit-time `oracle` account not validated against the queue, Low

`RequestOpen`/`RequestTemplateOpen` pass `oracle` unchecked into `RandomnessCommit` (lib.rs:1040-1058; opening.rs:357-375). Verified not exploitable through Switchboard (reveal re-verifies oracle/seed binding, post-CPI re-check at lib.rs:1144-1154); worst case is the designed timeout. Keep as defense-in-depth: pin or queue-check the oracle after commit.

### L4 — cNFT proof cap of 16 can strand prizes, Low

`MAX_BUBBLEGUM_PROOF_ACCOUNTS = 16` (collections.rs:529-544): deep trees with thin canopy make claim/reclaim permanently undeliverable. Creator-chosen at funding; reject deep trees at fund time or document the canopy requirement.

### L5 — `Migrate` route is permissionless, Low (today)

`process_migrate` (lib.rs:1379-1401) is reachable by any third party on any program-owned account. Today it is a validate-only no-op (pina.toml `auto = true`, no historical versions), so not exploitable — but the day a real schema migration ships, strangers can force-upgrade active accounts at a time of their choosing. Gate it behind the authority before shipping any non-trivial migration.

### I1 — License check fails on permissive-but-unlisted licenses, Informational

`cargo deny check` licenses FAILED on `Unicode-3.0`, `BSL-1.0`, `ISC`, `0BSD` variants (host-side CLI/test deps only; the on-chain program's dep tree is clean). Add them to `deny.toml` allow-list; not security.

### I2 — Local clippy broken for the pinned nightly, Informational

`rustup`'s clippy component for `nightly-2026-02-20` fails to install locally (component conflict), which makes every bare `cargo` invocation error before running. Tests/clippy were executed with explicit `+nightly-2026-02-20` / `+stable` overrides and pass clean. Fix the local toolchain install so `verify:all` keeps working.

### I3 — Switchboard on-chain source privatized, Informational

`docs/security-review.md`'s assertion that "Switchboard validates its own state, escrow, stats, and LUT PDAs during CPI" is currently unfalsifiable from public source. The close-time `reward_escrow` substitution has no theft path even under the worst case (escrow rent dust only; SPL close requires owner signature). Keep the devnet compatibility gate before every release; consider asserting `reward_escrow == ATA(wSOL, randomness)` pre-CPI.

## Invariants verified (hold)

- **Solvency/collateralization:** v1 worst-case liability (`(supply + pending) * max_reward`) re-evaluated at every supply/pending/payout/refund/withdraw change, with live supply re-read from the mint (lib.rs:599-623, 1070-1197). Template issuance capped by pristine exact-supply lock (templates.rs:1555-1578, 1684-1707) with lifetime `total_bundles` cap.
- **Deposit conservation:** append-only zero-slot funding with duplicate-mint rejection (templates.rs:1175-1213); escrow = bundle ATA with delegate/close/freeze rejected (templates.rs:1351); SOL claims re-check `owed` against live lamports (claims.rs:547-563).
- **Authority gating:** every privileged handler requires the stored authority as signer (`assert_template_authority`, `assert_authority_address`); no handler trusts an unsigned authority account.
- **Randomness binding:** opening PDA is the Switchboard authority; commit binds seed slot; reveal re-verified post-CPI including `reveal_slot > seed_slot` and `value == args.value` (lib.rs:1144-1154; opening.rs:457-465). Rejection sampling is uniform (Lemire threshold, proptest coverage). Entropy commits before the box burns.
- **Allocation:** FIFO via `next_allocation`, revision snapshots bind eligible prefix, draws without replacement, exhausted slots skipped (claims.rs:95-117, 140-178; kani proof of single-unit consumption).
- **Claims:** recipient-bound, per-asset claim bits, quantity-capped, badge mints revoke authority on final copy (claims.rs:373-416, 699-733).
- **Recovery:** only undrawn inventory, requires retirement + zero supply + zero pending (retirement.rs:106-152); allocated-but-unclaimed stays reserved.
- **Account safety:** canonical bumps everywhere; `close_account_zeroed` wipes data (kills close-and-revive); compact accounts reject hidden tails (templates.rs:369-400); fixed wire types reject trailing bytes; future schema versions fail closed.
- **Bubblegum cNFT path (verified this audit, new):** pinned V1 transfer ABI; V1 leaves are re-instantiated with `new_owner == delegate` (delegate cleared on every transfer), so escrowed pool leaves are fully controlled by the pool PDA. No analogue of H1 exists on the compressed path.
- **Off-chain:** playground wallets are test-only, loopback-gated, and refuse to sign on unexpected networks/config (apps/web/src/lootbox/playground.ts:213-230); CLI loads keypairs from files only, no logging of key material found.

## What was and was not reviewed

- **Reviewed:** all 8 program source files line-by-line; `switchboard_randomness_cpi` crate; pina 0.19.0 trust-base helpers (`impls.rs`, `traits.rs`); Metaplex Core and Bubblegum upstream sources at the program's pinned commits; CI, deny.toml, SECURITY.md, playground key handling, CLI key loading; tooling passes above.
- **Not reviewed (out of scope or unavailable):** deployed bytecode (pre-release); Switchboard on-chain source (privatized — I3); the Surfpool test harness's own RustSec exceptions (documented separately by the team); full Playwright/React app logic beyond wallet handling; Jupiter/DAS proxy internals.
- **Residual risk:** the three-layer review found the economics layer structurally sound (fully escrowed, no market-valued collateral), but H1 shows the adapter boundary is where this protocol's risk concentrates. Every external-asset adapter (Core, Metadata, Bubblegum, Token-2022 extensions) carries the same class of question: _which authorities survive custody transfer?_ The devnet compatibility gates in the release checklist are the right control — keep them blocking.
