# Security Review

Review date: 2026-09-03\
Scope: lootbox program, generated account surface, handwritten SDK validation, test oracle boundary, and playground gateway\
Reviewer: internal implementation review plus automated pull-request review; this is not a substitute for an independent production audit

## Result

No known critical, high, or medium findings remain open in the deployable program, SDK, or web workspace. Several high-impact design flaws and defense-in-depth issues were found while building and reviewing the MVP, then fixed before this report. The full SBF path passes offline Surfpool tests against separate lootbox and oracle artifacts, including adversarial attempts.

## Security invariants

1. A user loses a box before its random result can be known.
2. Only an account owned by a compiled-in Switchboard program can supply entropy.
3. The opening PDA is the randomness authority; neither holder nor lootbox authority can re-commit, reveal, or close directly.
4. Reveal and payout are atomic; recipient-authorized timeout pays only the minimum outcome and never creates a retry, so suppressing an off-chain proof cannot improve the result and outsiders cannot force the floor.
5. Every mint, vault, lootbox, receipt, queue, oracle, randomness account, and recipient is bound to its expected address.
6. Vault balance excluding rent always covers every minted or pending box at the maximum payout.
7. Outcome weights become immutable before boxes exist, their sum cannot exceed `u32::MAX`, and every revealed receipt has a terminating selection path.
8. A receipt reaches exactly one terminal state and pays only its stored recipient.
9. Arithmetic failure aborts; it never wraps into a smaller liability or weight domain.

## Threat review

### Authority abuse

The lootbox authority can choose the initial odds, mint within the fixed maximum, and delay minting. Once sealed, it cannot edit rewards, seize boxes, withdraw live collateral, redirect payouts, prevent third-party settlement, or prevent a recipient-authorized timeout. A malicious front end can still mislabel client-side names; consumers should derive numeric odds and rewards from `LootboxState`.

### Oracle manipulation

The program assumes the configured Switchboard deployment and queue correctly verify gateway proofs and generate unpredictable randomness. Ownership/layout checks prevent user-authored fake accounts. Opening-PDA authority plus atomic init/commit/burn and reveal/settle remove holder-controlled state changes. A minimum-reward timeout removes the remaining economic benefit of off-chain proof suppression. Oracle compromise, queue misconfiguration, ABI drift, or protocol failure remains an external trust risk.

### Account confusion

All program-owned accounts validate discriminators, owners, stored parents, canonical seeds, and bumps. Opening actions bind randomness, queue, oracle, seed, and recipient. Token accounts must be canonical ATAs. Known system, token, ATA, slot-hashes, clock, wrapped-SOL, lookup-table, and oracle program addresses are asserted where used; Switchboard validates its own state, escrow, stats, and LUT PDAs during CPI.

### Arithmetic and distribution

Supply, counters, weights, payouts, liability, and withdrawal minima use checked operations. Outcome weights are positive and capped in aggregate. Rejection sampling avoids practical modulo bias and has a deterministic terminal fallback. Zero-lamport outcomes remain valid intentional no-prize results.

### CPI and rollback

Mint, burn, account creation, oracle transitions, account cleanup, and SOL movement use fixed-shape CPI helpers. State guards do not cross mutable CPIs. Every multi-step transition shares one Solana instruction boundary, so a downstream failure rolls back the oracle and lootbox state together. Settlement validates recipient and pre-state before reveal, then marks the receipt terminal before payout.

## Verification evidence

- Rust unit/property tests cover instruction decoding, outcome boundaries, bounded selection, liability counting, reveal-data decoding, and SDK planning.
- TypeScript and Dart unit tests cover collateral math, invalid weights, negative/range values, and Switchboard reveal-data decoding.
- The Surfpool test deploys two SBF artifacts and proves create → configure → fund → seal → mint, then request-time oracle init/commit/burn → settle-time reveal/payout → oracle/receipt close, plus timeout floor payout → oracle/receipt close.
- The adversarial Surfpool journey rejects over-minting, reserved-fund withdrawal, excessive weights, preinitialized randomness, direct re-commit, direct reveal, early refund, outsider-forced timeout, and payout redirection; it checks that rejected redirection does not consume the reveal.
- React component and Playwright tests cover the user-visible commit/burn/reveal states on desktop and mobile.
- `cargo clippy`, Pina security lint, TypeScript checks, Dart analysis, dprint, `cargo audit`, `cargo deny`, pnpm audit, SBF builds, and the production web build are release gates.

The production workspace, test-oracle workspace, and pnpm workspace have no known dependency advisories at review time. The isolated Surfpool host harness inherits advisories from Surfpool/Solana's legacy transitive graph (`RUSTSEC-2024-0344`, `RUSTSEC-2022-0093`, `RUSTSEC-2026-0258`, `RUSTSEC-2024-0421`, `RUSTSEC-2026-0104`, `RUSTSEC-2026-0098`, and `RUSTSEC-2026-0099`). It runs offline, is excluded from the production workspace, and none of those crates are linked into either SBF artifact or distributed SDK. This tooling risk should be removed when Surfpool's dependency graph permits an upgrade.

## Residual risks and release gates

- This code has not received an independent audit or mainnet adversarial history.
- The compact Switchboard integration pins external discriminators, account ordering, and binary layout. Monitor upstream releases and rerun a real devnet compatibility test before every program release.
- Switchboard `randomness_close` deactivates its per-randomness lookup table, but the address lookup table's cooldown prevents reclaiming that LUT rent in the same call. This is an [open upstream lifecycle limitation](https://github.com/switchboard-xyz/on-demand/issues/9), not locked lootbox reward collateral.
- The timeout guarantees only the configured minimum reward; it cannot guarantee oracle availability, the originally sampled outcome, or transaction inclusion.
- Full maximum-reward collateralization is safe but capital-inefficient.
- V1 supports SOL and classic SPL Token boxes only; it does not support Token-2022 extensions, SPL/NFT reward inventory, or bundles.
- Upgrade-authority policy, deployment reproducibility, multisig control, monitoring, and incident response must be decided before public deployment.

Recommended production gates: independent audit, devnet soak against the live Switchboard program, reproducible binary verification, multisig upgrade authority, capped launch supply/value, monitoring for pending receipts and vault coverage, and a published incident process.
